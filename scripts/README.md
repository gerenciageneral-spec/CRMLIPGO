# Scripts SQL del CRM

Ocho scripts que levantan el CRM sobre la base de datos de Supabase.

## Orden de ejecución

Hay que correrlos **en orden**: cada uno se apoya en lo que creó el anterior.

| # | Script | Qué hace | Toca tablas de LIPgo |
|---|---|---|---|
| 181 | `crm_fundacion` | Secuencias de pedido, columnas comerciales, tabla de parámetros | **Sí** |
| 182 | `crm_prospectos` | Embudo, prospectos con GPS, actividades, agenda | No |
| 183 | `crm_precios` | Listas de precios y resolución de precio | No |
| 184 | `crm_cotizaciones_pedidos` | Cotizaciones, pedidos y doble autorización | No |
| 185 | `crm_cartera_comisiones` | Cuentas por cobrar, pagos, aging y comisiones | No |
| 186 | `crm_permisos` | 22 columnas `crm_*` en `permisos_usuarios` | **Sí** |
| 187 | `crm_rpc_proyeccion` | La función que escribe el pedido en LIPgo | **Sí** |
| 188 | `crm_vendedores` | Datos comerciales del vendedor y verificación final | No |

## Antes de correr el 181

**La base de datos es la misma que usa LIPgo en producción.** El 181, el 186 y
el 187 tocan tablas que LIPgo lee y escribe todos los días. Conviene:

1. Leer el encabezado del 181 entero. Explica por qué las secuencias se crean
   como se crean y por qué LIPgo puede seguir insertando ids explícitos sin
   enterarse.
2. Comprobar en Supabase si `pedidoscabecera.idpedido` es `identity`. Si lo
   fuera, el `SET DEFAULT nextval(...)` falla y hay que usar
   `ALTER ... SET GENERATED BY DEFAULT`. El script lo detecta y avisa, pero es
   mejor saberlo de antemano.
3. Después de correrlo, **abrir LIPgo y crear un pedido**. Debe seguir
   funcionando igual. Es la prueba de que las secuencias no rompieron nada.

## Cómo están escritos

Siguiendo la convención heredada de LIPgo, que vale la pena conservar:

- **Encabezado que explica el porqué**, no solo el qué. Quien lo lea dentro de
  un año necesita saber qué problema resolvía.
- **Aditivos e idempotentes**: `add column if not exists`, `create table if not
  exists`. Correrlos dos veces no rompe nada.
- **Verificación al final**, solo lecturas, para confirmar que quedó aplicado.
- **Reversión comentada**, con la advertencia de lo que NO se revierte (un
  pedido ya proyectado a LIPgo sigue allí; un archivo ya subido al Storage
  sigue subido).

Los que tocan dinero o producción ajena lo dicen en el encabezado: son los que
merecen una lectura distinta.

## Convención para los siguientes

Consecutivo de tres dígitos, continuando desde el 188:

```
189_add_lo_que_sea.sql
190_verificar_lo_que_sea.sql
```

El número dice en qué orden se fueron necesitando, que es el orden en que hay
que correrlos en una instalación nueva. No es una fecha ni una versión.

Para saber el siguiente:

```bash
ls scripts/*.sql | sort | tail -1
```

## Nota sobre el esquema heredado

Las tablas que el CRM reutiliza —`clientes`, `productos`, `bodegas`,
`pedidoscabecera`, `pedidosdetalle`, `vendedores`— **no tienen DDL en este
repositorio**: existen en Supabase desde antes y se crearon fuera de control de
versiones.

Si hace falta consultar cómo llegaron a ser lo que son, los 180 scripts
originales de LIPgo están en el historial de Git de este repositorio (antes del
commit que los eliminó) y en el repositorio `gerenciageneral-spec/LIPGO`.

Dos cosas del esquema heredado que conviene tener presentes al trabajar con él,
porque no son evidentes y ya causaron problemas:

- **`pedidosdetalle.producto` guarda el NOMBRE del producto, no su id.** LIPgo
  une por texto (`detalleoc.producto = productos.nombre`). Por eso el script 187
  valida que cada nombre exista en el catálogo antes de escribir: un nombre que
  no coincida entra sin error y revienta después, en el flujo de cargue.
- **El nombre de la columna de empresa varía por tabla**: `id_empresa` en
  `clientes`, `productos` y `vendedores`; `idempresa` en `bodegas`. Las tablas
  nuevas del CRM usan todas `idempresa`, sin guion bajo.
- **`activo` es TEXT, no boolean.** En `vendedores`, `productos` y otras tablas
  heredadas guarda las cadenas `'true'` / `'false'`. Usarla como condición
  booleana directa falla con *"argument of WHERE must be type boolean"*, y
  compararla con `coalesce(x, true)` falla con *"COALESCE types text and
  boolean cannot be matched"* — este último apareció al correr el 188 por
  primera vez. Para leerla:

  ```sql
  lower(trim(tabla.activo::text)) in ('true','t','si','1')
  ```

  Las tablas nuevas del CRM sí declaran `activo boolean not null default true`,
  que es lo correcto; la conversión solo hace falta al leer las heredadas.
